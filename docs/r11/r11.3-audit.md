# R11.3 Injection Testing Engine Audit

## Existing architecture and reuse points

| Existing capability | R11.3 reuse | Boundary retained |
| --- | --- | --- |
| R1 policy and R3 HTTP engine | An injected `httpengine.Client` is the only execution path. | R11.3 must not resolve, dial, follow redirects, build a transport, or replace policy evaluation. |
| R2 evidence | Existing canonical endpoint/parameter identities and append-only observations remain the evidence authority. | Injection tests cannot store request values, cookies, authorization data, or full responses. |
| R7 controlled fuzzing | The `fuzzing` package already supplies bounded generic mutation concepts, structural baseline comparison, dynamic timestamp/UUID normalization, header redaction, reflection detection, and coarse error classes. | R11.3 must not turn R7’s generic profiles into uncontrolled payload generation. |
| R8 validation | R8 accepts bounded validation input and produces `observed` results with reproducibility keys. | R11.3 emits injection signals; it never creates a confirmed finding. |
| R9 intelligence | R9 groups validated evidence using existing subject/rule correlation. | R11.3 does not add duplicate finding or root-cause correlation logic. |
| R10 and R10.5 | Identity metadata stays secret-free; global budget, rate, concurrency, cancellation, and phase lifecycle controls bound any future active orchestration. | Authentication attacks, credential testing, scheduler changes, and policy bypasses remain out of scope. |
| R11.1 request mutation | R11.1 owns immutable memory-only request templates and safe per-location mutation. | R11.3 composes a small approved payload set into variants; it must not rewrite the mutation engine. |
| R11.2 discovery | Project-scoped R2/R5/R6-derived candidates guide parameter selection; its verifier is the nearest active-module pattern. | Discovery candidates are not findings and do not authorize testing by themselves. |

## Missing abstractions and planned implementation

R11.3 needs a small `internal/injection` package containing an immutable payload registry, injection test plan, baseline/signal model, and a runner that accepts existing R3 plus R10.5 controls. The initial implementation will allow only deterministic, non-destructive, short safe canaries for selected SQL, NoSQL, SSTI, parameter-pollution, header, and path/input signal classes. Command injection remains signal-only: no shell, process, callback, or operating-system execution is permitted.

All tests will be project-scoped, parameter-specific, limit checked before work, and selected from a bounded class/profile registry. The plan will hand signals to R8 through an explicit adapter contract and preserve R9 correlation as a later consumer; neither handoff creates a finding.

## Trust boundaries and security risks

Candidates, local templates, payload selectors, response bodies, headers, and identity metadata are untrusted. Payloads are sensitive by nature even when safe, so they remain memory-only and are represented in serialized data only by stable identifiers and hashes. The engine must reject sensitive headers, unsafe methods, cross-project identities, unsupported content types, oversized bodies, excessive payload count, cancellation after each stage, and all attempts to convert response timing or reflection alone into confirmation.

Active mode must remain explicitly authorized. Every outbound request must consume the shared R10.5 budget and pass through the injected R3 client, which retains R1, SSRF/destination, DNS, redirect, and transport controls. R11.3 must stop cleanly on a budget, context, policy, or service-stability failure. R11.4 and later stages remain unstarted.
