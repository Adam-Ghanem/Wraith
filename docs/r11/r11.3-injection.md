# R11.3 Injection Testing Engine

R11.3 adds a bounded, project-scoped injection-testing engine. It is an evidence producer rather than an exploit framework: plans use existing R2 endpoint and parameter identities, compose a small approved payload registry through R11.1, and compare a baseline response with a single bounded test response by reusing R7 analysis. It does not create vulnerability findings.

| Control | R11.3 behavior | Boundary retained |
| --- | --- | --- |
| Authorization and scope | Planning requires explicit authorization intent and matching project-local endpoint and parameter identities. Active execution requires explicit `Execute` and authorization again. | Discovery candidates never authorize testing by themselves. |
| Payloads | The immutable default registry contains eight short, non-destructive canaries covering SQL, NoSQL, command, SSTI, parameter pollution, header, and path/input classes. | Values are memory-only and are never emitted in JSON, evidence, or fingerprints. |
| Request composition | R11.1 `ComposePayload` applies one registered value to one eligible R2 parameter. | The engine does not duplicate request-mutation logic or accept arbitrary payload text. |
| Execution | The caller supplies the existing R3 client and R10.5 budget, global rate, and concurrency controls. Only `GET` and `HEAD` are accepted. | R11.3 creates no direct HTTP client, resolver, socket, DNS request, transport, or subprocess. R1 remains at the R3 boundary. |
| Response analysis | R7 compares structural baseline and test snapshots for coarse error classes, reflection, and bounded differential indicators. | Timing or reflection alone is not confirmation. |
| Evidence | Each signal can persist one redacted R2 injection observation with metadata only. | Request values, cookies, authorization headers, full bodies, and credential material are not persisted. |
| Validation and correlation | A signal can be submitted through an explicit validation interface; R8 validates and R9 later correlates validated evidence. | The runner keeps `FindingsCreated` at zero and has no finding creation path. |

The planner supports `safe`, `standard`, and `deep` profiles, but profile selection remains a bounded registry filter rather than a payload generator. All plan limits are validated before work. The active runner sends at most a baseline and one payload request per planned test, obeys cancellation and duration limits, rejects unsafe methods, and stops immediately after a `429` response to avoid compounding service instability.

The command surface is intentionally planning-first:

```text
wraith inject [plan] TARGET --project PROJECT --authorized [--class CLASS] [--profile safe|standard|deep] [--max-tests N] [--dry-run] [--output json] [--db PATH]
```

The CLI produces a plan or dry-run output only and performs no active network execution. The library runner is the separately explicit execution seam, requiring injected R3/R10.5 dependencies and `Execute: true`.

## Deliberate limits

R11.3 excludes destructive payloads, operating-system command execution, out-of-band callbacks, credential attacks, authentication testing, write methods, autonomous crawling, arbitrary user payloads, raw request/response persistence, confirmation, reporting, and direct R9 correlation. R11.4 and later stages are not started by this branch.
