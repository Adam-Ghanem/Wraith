# R11.4 Audit — Finding Validation and Evidence Correlation

R11.4 begins from R11.3 signals and does not create a new scanner, payload source, transport, evidence database, or final-finding model. The desired outcome is a bounded, project-scoped validation result and finding candidate that can be handed to the existing R9 correlation layer. A signal remains a hypothesis until a controlled reproduction produces sufficient redacted evidence.

| Existing component | Reuse in R11.4 | Boundary retained |
| --- | --- | --- |
| R1 and R3 `httpengine.Client` | The validation runner accepts the existing policy-aware client for every baseline or mutation request. | R11.4 creates no HTTP client, transport, DNS resolver, dialer, redirect handler, or socket. |
| R2 `evidence` | Canonical endpoint and parameter identities remain the project-scoped subjects; append-only observations persist redacted validation evidence. | No alternate evidence database, raw payload, credential, cookie, authorization field, or response body persistence. |
| R7 analysis | `fuzzing.AnalyzeResponse` supplies normalized structural fingerprints, error classes, and reflection detection. | R11.4 does not create uncontrolled mutations or reinterpret a differential as confirmation by itself. |
| R8 `validation` | Existing validators evaluate bounded responses and produce `observed` results with reproducibility keys. | R11.4 may adapt the contract but does not bypass R8 or create accepted/confirmed lifecycle states from a response difference. |
| R9 `intelligence` | Validated candidates can be translated into project-scoped R9 candidates for deterministic grouping and correlation. | R11.4 does not replicate R9 grouping, confidence score, deduplication, or root-cause logic. |
| R10 identity model | Identity context remains an opaque selector; it is never converted into credential storage or fallback identity selection. | Lost authentication yields an inconclusive result rather than a retry with another identity. |
| R10.5 `pentest` | Shared request budget, global rate limiter, concurrency controller, cancellation, and phase model bound active work. | R11.4 does not add a scheduler, worker, unlimited retry loop, or independent resource governor. |
| R11.1 and R11.3 | Existing immutable request templates, bounded payload registry, signal model, and `ComposePayload` produce the minimum reproduction requests. | R11.4 creates no new injection class or arbitrary payload family. |

## Validation flow

The runner must fail closed before any request unless the signal, endpoint, parameter, project identity, profile, and active authorization context are coherent. A safe profile performs the smallest bounded reproduction: baseline, registered payload, and a confirmation baseline/payload pair only when the profile permits it. Every request uses the supplied R3 client and consumes the shared R10.5 request, rate, and concurrency controls.

The response evaluator compares only redacted structural metadata. It accounts for status, normalized fingerprints, content type, bounded length deltas, error classes, and reflection. It suppresses dynamic-only variation and marks rate limits, transient 5xx responses, timeouts, connection failures, and inconsistent repetitions as inconclusive rather than vulnerabilities. A `429` halts validation immediately.

## Gaps and minimal R11.4 additions

The existing packages lack a project-scoped object that ties an R11.3 signal to reproducibility attempts, evidence references, repeatability, a bounded confidence assessment, and an R9-ready candidate. R11.4 therefore needs a focused package with validation candidate/result/diff/finding-candidate models, deterministic fingerprints, a runner accepting only injected dependencies, and narrow R8/R9 adapter interfaces. It must not add a second finding store.

## Trust boundaries and implementation plan

Signals, endpoint/parameter identities, templates, response bodies, headers, R10 identity selectors, and transport outcomes are untrusted inputs. Payload values remain memory-only. Every public model must reject cross-project references, unbounded collections, invalid profiles, stale/malformed signal state, sensitive fields, and unsupported classes. The implementation will first lock those rules with unit tests, then add the R3/R10.5-controlled runner, redacted R2 evidence emission, R8/R9 adapters, plan/dry-run CLI integration, fuzzing, benchmarks, and a final egress/security audit.
