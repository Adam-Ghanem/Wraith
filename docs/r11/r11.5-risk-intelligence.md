# R11.5 Security Findings and Risk Intelligence

R11.5 is a local, deterministic risk-intelligence layer. It accepts only an R11.4 **validated** temporary finding candidate with repeatable evidence and a non-empty R9 correlation identifier. It produces a project-scoped security finding, explainable risk assessment, explicit lifecycle state, and stable local listing/summary output. It does not validate, correlate, scan, generate payloads, or perform network activity.

| Input or action | R11.5 rule |
| --- | --- |
| Validation input | Rejected, inconclusive, malformed, cross-project, non-repeatable, or evidence-free R11.4 results fail closed and cannot create an active finding. |
| Finding fingerprint | SHA-256 over project, asset ID, endpoint ID, parameter ID, class, and subtype. Raw payloads, candidate fingerprints, credentials, headers, bodies, and session material are excluded. |
| Severity and confidence | Severity comes from the validated candidate hint. R11.4 confidence is preserved and is never treated as severity. |
| Risk scoring | Version `r11.5-v1` sums documented bounded factors: severity, confidence, repeatability, exposure, asset criticality, authentication context, data sensitivity, and exploitability. No timestamp, host heuristic, random value, or network state affects the score. |
| Risk bands | `0–19` informational; `20–39` low; `40–59` medium; `60–79` high; `80–100` critical. These thresholds are fixed for `r11.5-v1`. |
| Context defaults | Missing/invalid asset criticality, exposure, authentication, data sensitivity, or exploitability context becomes `unknown`/`none`; R11.5 does not infer it from hostnames or parameter names. |
| Lifecycle | Open findings may be accepted, resolved, suppressed, or marked false positive. Resolved/false-positive findings may reopen. Invalid transitions fail closed and history is append-only. |
| Suppression | Only the matching project and finding fingerprint can be suppressed; reason is mandatory; expiration cancels suppression rather than hiding the finding. |

The SQLite migration creates four project-scoped tables: `security_findings`, `finding_history`, `risk_assessments`, and `finding_suppressions`. Records are indexed for project status, severity, risk, asset, and finding history. The existing R2 observation store is referenced, not duplicated.

## Local commands

```text
wraith findings --project PROJECT [--severity LEVEL] [--status STATUS] [--class CLASS] [--min-risk N] [--asset ASSET] [--limit N] [--output terminal|json] [--db PATH]
wraith risk --project PROJECT [--output terminal|json] [--db PATH]
```

Both commands operate only on the local SQLite database. Findings are sorted by risk score descending, then severity, then finding ID. Output omits internal candidate fingerprints, payloads, request/response bodies, credentials, cookies, authorization data, and session material.

## Deliberate limits

R11.5 has no HTTP client, DNS resolver, socket, subprocess, scheduler, crawler, scanner, fuzzer, injection engine, validation loop, correlation implementation, external finding import, AI-based scoring, exploit instructions, or credential/secret storage. R10.5 recognizes `r11.5_risk` as a plan phase, but no automatic active phase adapter, report adapter, or R11.6 work is added.
