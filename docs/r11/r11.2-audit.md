# R11.2 Smart Content and Parameter Discovery Audit

## Existing architecture and reuse points

| Existing capability | Reusable R11.2 role | Boundary retained |
| --- | --- | --- |
| R1 policy | Authorizes every future verification request. | R11.2 must not evaluate or replace the policy engine. |
| R2 evidence | Canonical web-asset, endpoint, parameter, and append-only observation identities. | Candidate identities must reference R2; no second asset/endpoint model. |
| R3 HTTP engine | The only allowed active verification transport. | No direct HTTP, DNS, socket, redirect, or destination-safety implementation in R11.2. |
| R4 crawler | Existing local crawl/form/link/script evidence. | R11.2 only consumes evidence and never starts an independent crawler. |
| R5 inventory | Deterministic project-scoped endpoint/parameter projection. | R11.2 derives candidates, not a replacement endpoint inventory. |
| R6 static JavaScript analysis | Local, value-minimized URL, request, parameter, route, and technology references. | No JavaScript execution, browser, or new parser runtime. |
| R7.5 content discovery | Explicit local wordlist limits, soft-404 comparison, and bounded R3 runner patterns. | Reuse controls; do not create an unlimited scanner or alternate transport. |
| R10/R10.5 | Project identities, secret-free contexts, run history, budget/rate/concurrency primitives. | No credentials/secrets in candidates or discovery evidence. |
| R11.1 | Immutable request mutation plans for selected R2 parameters. | R11.2 decides **what** to consider; R11.1 decides **how** a selected request can be mutated. |

## Missing abstraction and planned implementation

R11.2 needs a project-scoped `DiscoveryCandidate` domain model with a deterministic fingerprint, candidate type, independent provenance records, confidence, discovery priority, and a non-vulnerability status. Planning will consume R5 inventory plus R2-compatible sources, normalize only through R2 URL rules, merge equivalent project-local candidates, and cap all source and output volumes.

The initial safe slice will prioritize passive candidate planning and explicit local-wordlist handling. Any future active verification is a separate adapter with explicit `--verify`, an R1-approved/R3-only client, R10.5 budget/rate/concurrency controls, cancellation, response classification, and value-redacted R2 observations. Candidate generation itself makes no network request.

## Trust boundaries and limitations

Evidence, local wordlists, CLI options, and optional authenticated context metadata are untrusted inputs. The implementation must reject malformed URLs, userinfo, unsupported schemes, ambiguous hosts, traversal-like paths, oversized files, excessive entries, sensitive values, and project mismatches. It must not persist raw query values, cookies, authorization data, tokens, passwords, or private-key material.

R11.2 discovery candidates are neither verified resources nor vulnerabilities. R4 continues to crawl, R8 continues validation, R9 continues correlation, and R11.3 remains unstarted.
