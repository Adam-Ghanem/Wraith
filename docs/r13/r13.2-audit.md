# R13.2 Active Assessment Execution Engine — Pre-Implementation Audit

**Baseline.** R13.2 starts on `feature/r13.2-assessment-execution` at R13.1 commit `3aa3998`. `origin/main` is verified at `42cb8b2` and remains out of scope. The change is a synchronous, local execution lifecycle for a previously validated R13 assessment plan; it is neither a scanner nor a scheduler.

## Existing execution flow and ownership

| Concern | Verified owner and reusable seam | R13.2 boundary |
| --- | --- | --- |
| Plan model | `internal/assessment.PlanActiveAssessment`, `ValidateTasks`, deterministic task IDs and task dependencies | Revalidate plan/project/scope/profile/limits and add execution-only checks such as adapter registration and cycle detection. |
| Adapter dispatch | `internal/assessment.AdapterRegistry.Execute` and `TaskAdapter` | Use this registry only. Never create a second adapter registry or dynamically select unknown adapters. |
| Budget, concurrency, rate | `internal/pentest` `BudgetManager`, `ConcurrencyController`, `GlobalRateLimiter`, and `RunContext` | Construct and share one R10.5 control set per assessment execution. No competing limiter or budget ledger. |
| Authorization and destination safety | R1 policy evaluator/gateway and R3 `httpengine` | R13.2 owns no authorization evaluator, DNS, socket, redirect, TLS, proxy, retry, or HTTP client. Active owners must continue to pass R1/R3. |
| Evidence and findings | R2 immutable observations; R11.4 → R9 → R11.5 lifecycle | Normalize owner result references only. No R13.2 evidence repository, payload persistence, or local finding creation. |
| Current persisted lifecycle | R10.5 `pentest_runs`, `pentest_phase_runs`, and append-only `pentest_events` | Reuse project/run/event storage where its status vocabulary suffices. Task execution maps to the existing phase record and preserves blocked detail in a bounded reason/event instead of adding an execution database. |
| CLI | `wraith pentest assessment plan` is a no-network in-memory planning command | Add an explicit `run` path and retain plan compatibility. Execution requires `--project`, `--authorized`, `--scope-version`, and `--profile`; dry-run never invokes an adapter. |

## Current model, lifecycle, and controls

R13 scope snapshots include project, scope version, canonical target, explicit authorization, profile, expiry, and bounded request/concurrency/rate/duration limits. The existing R13 executor is sequential, rechecks expiry prior to each task, honours context cancellation, and blocks dependent work when a predecessor does not complete. R13.1 adds a secret-free `TaskContext`, one binding per known task type, identity validation for adapter results, and required R10.5 shared controls.

R10.5 already has explicit run transitions (`created → planning → running → completed|partial|failed|cancelled`) and phase records (`pending|running|completed|failed|skipped|cancelled`). It uses a mutex-protected atomic budget counter, a channel-backed bounded concurrency controller, and a mutex-protected, cancellation-aware global rate limiter. Its lifecycle emits project-scoped events with `{}` metadata, which is compatible with secret-minimized R13.2 audit events.

## Threat and failure review

| Risk | Required R13.2 control |
| --- | --- |
| Project or target mismatch | Validate task, scope, and request project/target identity before any task becomes runnable. |
| Scope expiry or revoked authorization | Recheck before execution and before dispatch; cancel pending work on expiry. Network owners continue their per-request R1 checks. |
| Budget race | Consume exclusively through the R10.5 mutex-protected manager before a task is dispatched. Concurrency tests must prove exhausted work never starts. |
| Dependency race or cycle | Fail the full plan before execution on cycle/missing dependency; use deterministic priority-descending, task-ID-ascending ready ordering. |
| Cancellation leak | Derive global/per-task context deadlines and pass the task context to the adapter. Mark never-started work deterministically. |
| Missing/malformed adapter | Fail validation or mark the affected task blocked with a bounded reason; never panic or fall back to a different owner. |
| Secret leakage | Context, results, persistence metadata, errors, events, JSON, and terminal output use identifiers/counts/reason codes only. Reject secret-like context values rather than redact-and-run. |
| Duplicate execution | Require one explicit execution request and a fresh run ID; R13.2 will not introduce background workers, automatic replay, or automatic resume. |

## Exact R13.2 implementation boundary

R13.2 will add a focused `internal/assessmentexec` package that owns an explicit task state machine, whole-plan validation, deterministic dependency-aware execution, timeout/cancellation propagation, normalized secret-free results, and injected audit persistence. It will invoke `assessment.AdapterRegistry` rather than directly calling crawler, discovery, fuzzing, injection, validation, correlation, or finding packages. CLI integration will construct the plan and existing R10.5 controls only after explicit authorization flags; dry-run validates the same plan and adapter binding but returns before dispatch.

R13.2 will not add a new HTTP transport, policy system, DNS resolver, socket dialer, payload class, mutation engine, scanner, task queue, background worker, resume replay, authentication mechanism, credential store, evidence store, findings/risk implementation, report engine, or R14 work.
