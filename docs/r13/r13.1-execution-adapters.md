# R13.1 Execution Adapters and Active Assessment Pipeline

R13.1 converts the R13 task callback into an explicit single-owner adapter registry. The registry maps each deterministic R13 task type to exactly one injected existing-component owner, passes only project/scope/task references plus the shared R10.5 run controls, and validates adapter results before recording task completion.

| R13 task category | Required owner | R13.1 rule |
| --- | --- | --- |
| Crawl, endpoint inventory, and JavaScript intelligence | Existing R4/R5/R6 implementations | Adapters preserve their existing R1/R3/R2 limits and identity model. |
| Baseline, discovery, mutation, fuzz, and injection | Existing R3/R11.2/R11.1/R7/R11.3 implementations | No new transport, payload, mutation, fuzz, or injection generator exists in R13.1. |
| Validation, correlation, finding, risk, and surface | Existing R11.4/R9/R11.5/R11.6 lifecycle owners | Raw adapter signals are never local findings. |
| Report | Existing R10.5/R12 output owner | No new report renderer or storage model is added. |

`TaskContext` intentionally contains no raw credential, cookie, authorization header, token, payload, or evidence body. `AdapterRegistry.Execute` requires the existing R10.5 budget, concurrency, and rate controls because it delegates via R13’s fail-closed executor. The registry has no HTTP client, resolver, socket, TLS configuration, redirect handling, subprocess, or persistence logic.

## Current explicit boundary

R13.1 supplies the registry and coordinator contract needed to inject real existing adapters. It does not silently configure crawler, fuzzing, injection, validation, finding, or graph adapters from incomplete state. If a caller cannot provide the R1/R3/R2/R10.5/R11 dependencies required by the owner implementation, it must not create an adapter; the task remains explicitly unsupported rather than bypassing architecture.

R13.1 does not add a distributed scheduler, queue, worker, external service, credentials, destructive testing, main merge, or R14.
