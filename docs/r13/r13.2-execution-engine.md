# R13.2 — Active Assessment Execution Engine

R13.2 turns an R13 assessment plan into a **bounded, synchronous, project-scoped execution lifecycle**. It is an orchestration layer only. It neither adds a scanner nor replaces R1 authorization, R3 transport, R2 evidence, R10.5 controls, or the R11 validation/finding lifecycle.

## Execution contract

The execution package is `internal/assessmentexec`. A caller provides an R13 plan, its project ID, an R13.1 `AdapterRegistry`, one shared R10.5 `RunContext`, and an authorization recheck function. The engine validates the complete request before dispatch. This includes project/task/scope identity, profile, expiry, dependency graph, registered owner, secret-free URL context, task timeout, and required shared controls.

| State | Meaning | Allowed next states |
| --- | --- | --- |
| `pending` | Validated and queued but not started. | `running`, `blocked`, `skipped`, `cancelled` |
| `running` | Budget consumed and adapter context created. | `completed`, `failed`, `cancelled` |
| `completed` | Owner returned a valid matching result. | Terminal |
| `failed` | Owner returned an error or malformed result. | Terminal |
| `cancelled` | Caller context, global deadline, task deadline, or authorization recheck stopped the task. | Terminal |
| `skipped` | Dry-run or expired authorization prevented work before dispatch. | Terminal |
| `blocked` | A dependency failed or the shared request budget was exhausted before start. | Terminal |

Ready tasks are selected deterministically by descending R13 priority and then ascending task ID. The current engine is intentionally synchronous rather than a second worker scheduler. Each dispatch still obtains the pre-existing R10.5 atomic budget, concurrency slot, and rate permission; no alternate budget counter, limiter, queue, retry mechanism, or goroutine pool is created.

## Authorization and dispatch

R13.2 calls its injected R1 authorization callback before execution, before each scheduling cycle, and immediately before `AdapterRegistry.Dispatch`. Therefore a revocation observed during a concurrency or rate wait prevents adapter control from being reached. The adapter registry also rejects expired scope snapshots using the caller’s deterministic clock, validates one registered owner for every known task type, and rejects a result whose owner, task ID, signal count, or evidence references are invalid.

> **No authorization means no adapter dispatch.** R13.2 itself performs no HTTP request, DNS resolution, socket dial, redirect processing, TLS configuration, proxy operation, or subprocess execution. Any owner that performs outbound work must continue to use its existing R1/R3-controlled component seam.

Task contexts contain only assessment, scope, task, and R10.5 control references. They exclude credentials, cookies, authorization headers, bearer values, API keys, raw payloads, and request bodies. Secret-like URL userinfo or credential-like query parameter names are rejected rather than redacted and executed. Evidence references are bounded identifiers and are rejected when blank, oversized, or secret-like.

## Timeout, cancellation, and results

The engine derives a global deadline from the plan duration. A caller may add a bounded per-task timeout; otherwise the task inherits the assessment duration. The shorter context is passed to the adapter and cancellation is normalized as `cancelled`. A failed dependency marks only its dependent pending task `blocked`; an unknown/missing adapter fails validation before any task begins.

Adapter signals remain **signals**. R13.2 neither writes an R2 evidence body nor creates a finding. Existing owner components retain evidence ownership, and any signal still follows the R11.4 → R9 → R11.5 validation/correlation/finding route where applicable.

## CLI and persistence

The explicit command is:

```text
wraith pentest assessment run TARGET \
  --project PROJECT \
  --authorized \
  --scope-version VERSION \
  --profile safe|standard|deep \
  --db wraith.db \
  [--dry-run] [--max-tasks N] [--max-requests N] \
  [--max-duration D] [--max-concurrency N] [--rate N] \
  [--task-timeout D] [--json]
```

The command loads the active R1 scope from SQLite, requires that its version match `--scope-version`, and evaluates the canonical target for `policy.ActionHTTP`. It derives the plan expiry from the shorter of the requested duration and the active authorization expiry. Dry-run performs scope, plan, owner, dependency, budget, and authorization validation but invokes no adapter and writes no execution lifecycle record.

Non-dry-run lifecycle persistence deliberately reuses R10.5’s project-scoped `pentest_runs`, `pentest_phase_runs`, and append-only `pentest_events` records. The execution maps tasks to existing phase records and writes `{}` event metadata; only bounded status/reason codes are persisted. No R13.2 migration or parallel execution store exists.

The repository deliberately does **not** auto-wire incomplete owner dependencies. The CLI registers explicit fail-closed owner placeholders until a caller supplies the established component dependencies required by a real owner adapter. A non-dry run records the resulting bounded partial lifecycle without triggering HTTP, DNS, socket, or subprocess activity. This preserves the R13.1 rule that an adapter must not be manufactured from incomplete capability state.

## Explicit non-goals

R13.2 adds no scanner, HTTP client, DNS resolver, socket client, payload class, mutation engine, injection engine, credential mechanism, secret persistence, findings engine, report renderer, background worker, arbitrary resume/replay behavior, external service, main merge, or R14 work.
